# 004 – RLS: checklist de testes

Rode `20260928000004_rls.sql` no SQL Editor **depois** de 001, 002 e 003.
Antes de rodar em produção, faça um backup ou teste num projeto de staging.

## 0. Pré-checagens (SQL Editor, somente leitura)

```sql
-- a) A trigger de cadastro (auth.users -> profiles) é security definer?
select t.tgname, p.proname, p.prosecdef
  from pg_trigger t join pg_proc p on p.oid = t.tgfoid
 where t.tgrelid = 'auth.users'::regclass and not t.tgisinternal;

-- b) Dono das tabelas e se o postgres ignora RLS (as RPCs dependem disso)
select tablename, tableowner from pg_tables where schemaname = 'public';
select rolname, rolbypassrls from pg_roles where rolname in ('postgres', 'supabase_auth_admin');

-- c) Colunas de orders/order_items (a trigger de operador libera só algumas)
select table_name, column_name from information_schema.columns
 where table_schema = 'public' and table_name in ('orders', 'order_items')
 order by 1, ordinal_position;
```

- (a) `prosecdef = true` é o esperado. Se for `false`, a policy `auth_admin_insert` cobre o caso.
- (b) As tabelas devem ser do `postgres` (ou `postgres` com `rolbypassrls = true`). Senão as RPCs SECURITY DEFINER esbarram no RLS.
- (c) Se o checkout ou a reserva alterarem alguma coluna além de `status`, `photo_url`, `concluido_em` (orders) ou `qty_reserved_total`, `qty_consumed_total` (order_items), inclua‑a em `v_livres` nas funções `guard_*`.

## 1. Depois de rodar (SQL Editor)

```sql
-- RLS ligado em tudo?
select tablename, rowsecurity from pg_tables where schemaname = 'public' order by 1;

-- Policies criadas
select tablename, policyname, cmd, roles from pg_policies where schemaname = 'public' order by 1, 2;

-- RPCs como SECURITY DEFINER
select proname, prosecdef from pg_proc
 where pronamespace = 'public'::regnamespace
   and proname in ('register_production', 'register_defect', 'assemble_kit', 'adjust_kit_stock',
                   'register_material_entry', 'set_machine_state', 'delete_user_keep_history');
```

- [ ] Todas as tabelas com `rowsecurity = true`.
- [ ] Nenhum NOTICE "SEM policy" para tabela que o app usa.
- [ ] As 7 funções com `prosecdef = true`.

## 4. OP_ESTOQUE (e OP_PRODUCAO, se houver usuário com esse papel)

Fluxos que precisam continuar funcionando:

- [ ] Login redireciona para `/operator/dashboard`; lista de pedidos pendentes carrega e o som de novo pedido toca (realtime em `orders`).
- [ ] **Operação**: trocar status/molde da máquina (`set_machine_state`), com histórico.
- [ ] **Produção manual**: lançar produção → peça sobe, material (kg) desce (`register_production`).
- [ ] **Defeitos**: registrar defeito → peça desce (`register_defect`).
- [ ] **Scanner**: montar kit → kit sobe, peças descem (`assemble_kit`).
- [ ] **Reserva**: reservar kits de um pedido → kit desce, reserva e movimentação criadas, `qty_reserved_total` atualizado.
- [ ] **Reverter reservas** pelo dashboard do operador → estoque volta, reserva fica "reversed".
- [ ] **Checkout (baixa)**: upload de foto, pedido vira Concluído, reservas consumidas, movimentações criadas, estoque baixado.
- [ ] **Estoque**: visão de kits/peças carrega.

O que deve ser **negado** (teste pelo console do navegador logado como operador, ex.: `await supabase.from("kits").update({estoque_atual: 999}).eq("id", 1).select()`):

- [ ] `update` em `kits`/`moldes`/`materials`/`machines` → retorna `[]` (0 linhas), nada muda.
- [ ] `insert` em `kits`, `machines`, `orders`, `order_items` → erro "new row violates row-level security policy".
- [ ] `delete` em `orders` → `[]`, nada apagado.
- [ ] `update` em `orders` mudando `cliente` ou `data_entrega` → erro "Operadores só podem concluir o pedido…".
- [ ] `update` em `orders` com `status: "Entregue"` → erro "Operadores só podem mudar o pedido para Concluído".
- [ ] `update` em `order_items` mudando `quantidade` → erro "Operadores só podem alterar as quantidades…".
- [ ] `update` em `profiles` (inclusive o próprio `role`) → `[]`, papel não muda.
- [ ] `select` em `profiles` → só o próprio perfil.
- [ ] `rpc("register_material_entry", …)` → erro "Apenas administradores…".
- [ ] `insert` em `stock_movements` com `user_id` de outra pessoa → erro de RLS.
- [ ] Acessar `/config/*` e `/dashboard/*` pela URL não carrega dados de outros usuários nem permite gravar.

## 5. Cadastro público (signUp com a chave anon)

- [ ] Chamar `signUp` com `options.data.role = "ADMIN"` sem estar logado → o perfil nasce **OP_ESTOQUE**.

## Riscos que continuam abertos

- **Cadastro público ligado**: a tela de Usuários usa `signUp` com a chave anon, então qualquer pessoa pode criar uma conta e virar operador (OP_ESTOQUE). Para fechar isso: desligar "Allow new users to sign up" em Authentication › Providers › Email e criar usuários por uma Edge Function com a service role (ou convidar pelo painel do Supabase).
- **Operador ainda escreve direto** em `orders` (checkout), `order_items` (quantidades), `order_item_reservations` e `stock_movements`, e chama `adjust_kit_stock` com qualquer delta. É o que as telas atuais exigem; o ideal é mover reserva/checkout/reversão para RPCs como as de produção.
- **Usuário excluído** com sessão aberta perde leitura e escrita direta na hora, mas as RPCs de estoque só checam `auth.uid()` até o token expirar (≈1 h).
- **Storage `order-photos`**: não é coberto por esta migração. Confira em Storage › Policies que só `authenticated` pode fazer upload.
